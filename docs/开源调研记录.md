共同上游意味着项目数量与独立实现数量并不相同。许可证、接口过时问题和实现缺陷也可能沿派生关系传递，应以具体文件与版本核验。

## 3. 关键源码观察如何转化为设计

| 观察 | 本项目设计建议 | 需要实测的条件 |
| --- | --- | --- |
| Web 会话与课堂 token 是不同层次 | 分开管理登录态和课堂态 | 微信已入课后如何取得监听凭据 |
| 示例取得 token 的路径包含 checkin | 不把监听设计成先验无副作用 | 出勤是否改变、是否存在更合适的已入课路径 |
| WebSocket 有新题、延时和时间线等消息 | 归一化为本项目内部事件 | 目标学校实际消息结构 |
| 示例合并处理 unlockproblem 与 extendtime | 对新发布和延时分开处理 | 同题重新发布的标识 |
| 初始连接可返回历史状态 | 去重状态持久化，区分实时与恢复 | 平台回放覆盖范围、结束题状态 |
| 移动包装项目存在后台断联报告 | 先做原生服务和深度锁屏实验 | 用户目标手机能否满足时延 |
| 部分项目支持远程通知 | 保留推送出口 | 是否接受持续在线监听端，以及可用设备推送渠道 |

## 4. 平台官方依据

| 资料 | 与规划关联的事实 |
| --- | --- |
| [AOSP：Application Sandbox](https://source.android.com/docs/security/app-sandbox) | 应用的数据与执行环境隔离，普通辅助 App 无法直接取得微信私有登录态 |
| [Android：通知权限](https://developer.android.com/develop/ui/compose/notifications/notification-permission) | Android 13 及以上普通通知涉及运行时授权 |
| [Android：通知概览](https://developer.android.com/develop/ui/compose/notifications) | 横幅、锁屏和渠道等行为受系统与用户设置影响 |
| [Android：时间敏感通知](https://developer.android.com/develop/ui/views/notifications/time-sensitive) | 原生高重要性通知可用于即时提醒，展示行为仍由系统管理 |
| [Android：从后台启动前台服务的限制](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start) | 不能任意在后台启动课堂监听服务，用户前台主动启动更符合首版流程 |
| [Android：前台服务类型](https://developer.android.com/develop/background-work/services/fgs/service-types) | 需要按用途声明类型；specialUse 有用途声明和发布审核条件 |
| [Android：前台服务超时](https://developer.android.com/develop/background-work/services/fgs/timeout) | Android 15 及以上相关目标版本条件下 dataSync 后台有累计时间预算 |
| [Android：Doze 与 App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby) | 深度休眠可暂停网络、延后工作，必须实测锁屏长连接 |
| [Android：PeriodicWorkRequest](https://developer.android.com/reference/androidx/work/PeriodicWorkRequest) | 周期任务最小间隔为 15 分钟，实际时间不精确，不适合秒级课堂事件监听 |
| [Android 14 行为变化](https://developer.android.com/about/versions/14/behavior-changes-14) | 普通提醒不能预设能够默认使用任意全屏打断能力 |
| [Android Keystore](https://developer.android.com/privacy-and-security/keystore) | 可保护应用加密密钥，用于凭据密文保存方案 |
| [Android 16](https://developer.android.com/about/versions/16) | 用户确定的首版平台为 Android 16，对应 API 36 |
| [Android 16 全应用行为变化](https://developer.android.com/about/versions/16/behavior-changes-all) | 前台服务一起运行的调度任务仍受 JobScheduler 配额影响 |
| [Android：长期 Worker](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running) | Android 16 长期 WorkManager Worker 可能耗尽任务预算，不应作为无限课堂监听的默认实现 |
| [小米推送产品说明](https://dev.mi.com/distribute/doc/details?pId=1533) | 自家系统通知通道不要求 App 常驻，可作为 Xiaomi 14 的推送验证候选 |
| [小米推送常见问题](https://dev.mi.com/xiaomihyperos/documentation/detail?pId=1545) | 其他系统的接收条件不同，不把小米推送直接当作多品牌通用后台保障 |

本轮还查看了 Apple 推送和后台策略资料。由于用户已经明确首版 Android，本规划没有扩展 iOS 开发范围。

## 5. 证据限制与后续核验

1. 部分页面是检索和网页缓存结果，不是冻结的完整源码快照；读取失败的文件没有被视为已审查。
2. GitHub API 只成功返回了部分仓库信息，其余请求出现连接错误。本轮不以不完整 API 结果排序项目活跃度，也不使用 star 数作为可靠性依据。
3. 本轮未运行仓库程序、未测试账号、未测试学校入口、未测试锁屏通知。
4. 雨课堂协议属于从社区实现观察到的候选内部接口；名称、鉴权、事件格式和有效期必须在目标环境重新验证。
5. 项目作者报告的 Cookie 有效期等经验不作为本项目固定常量；以实际返回、会话校验和过期行为为准。
6. 正式复用前补齐具体文件的作者、许可、上游来源；正式协议验证时保存版本号或提交、脱敏样本、设备信息与实验条件。

以上资料支持的结论是：已有协议与移动端经验可借鉴，值得开展独立登录和后台提醒可行性验证；尚不足以宣称目标方案已经可用。
