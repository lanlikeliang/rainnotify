# 手机实测、服务器取舍与首版决策

更新日期：2026-10-03（北京时间）。下一次真实课堂机会为用户提供的 **2026-10-09**，具体上课时段待补充；目前没有可控制发题的测试课堂。

## 1. 已确认的条件

- 普通版雨课堂，Android 16 多品牌手机，独立辅助 App。
- 提醒采用系统横幅、锁屏通知及声音/振动，需覆盖切换 App 和锁屏。
- 已明确区分亮屏锁定与完全熄屏：熄屏期间必须及时发声，当前不要求自动亮屏。0.0.4 在 Xiaomi 14 本 App 省电策略无限制下，通过一次约 30 秒本地熄屏有声测试；长期连接另行验证。
- Xiaomi 14 是首台验证手机，用户可以连接本电脑并授权 USB 调试。
- 用户自己登录真实账号，不在聊天中提供密码、Cookie 或课堂 token。
- 优先纯手机版；实测不达标时再讨论服务器，不提前部署。
- 如获取监听凭据必须进入课堂，允许用户明确点击“进入课堂并监听”；界面须说明可能同时记录签到。
- 真实发题只能在日常课堂观察，不应给教师或课堂成员发送测试消息，也不应自动答题。

## 2. 我如何获得手机实测结果

### 推荐：本机 USB 调试

用户把 Xiaomi 14 用可传输数据的 USB 线连接这台 Windows 电脑，在手机启用开发者选项、USB 调试，并在手机上批准本电脑的调试请求。Android 官方提供了此连接和授权流程：[实机调试说明](https://developer.android.com/studio/run/device)。

成功连接且测试 APK 编译完成后，我可通过 ADB 安装本项目的调试 APK、读取必要设备信息、查看本 App 日志并导出其私有诊断文件。用户仍负责微信扫码授权、正常课堂操作及实际通知感知反馈。

**连接授权不代表已经连接成功。** 2026-10-03 已通过 ADB 确认 Xiaomi 14 的 Android 16 连接，并成功构建通知验证 APK；安装和行为实测进度见 [当日记录](实测记录-2026-10-03.md)。真实雨课堂协议和发题尚未验证。

采集范围限定为本 App 和必要设备状态，不读取微信的私有文件或登录凭据，不默认导出全手机日志/完整系统 bugreport。

### 不连接电脑时

后续 APK 将内置“导出诊断报告”。用户完成课堂测试后导出 JSONL，将文件放进项目的 `diagnostic-reports/` 目录或作为附件提供；我分析该报告。这个方式可以验证离开电脑后的真实日常使用行为，但实时定位问题会比 USB 调试慢。

### 报告记录什么

| 信息 | 目的 |
| --- | --- |
| App 版本、匿名运行 ID、手机型号、Android/厂商系统版本 | 区分构建和机型条件 |
| 屏幕交互状态、休眠状态、省电状态和通知渠道状态 | 判断系统限制与提醒配置 |
| 网络连接、断线、重连和登录过期事件（接入网络模块后） | 定位数据连接问题 |
| 脱敏发布事件 ID、接收时间、解析结果、通知提交时间 | 判断漏提醒、重复提醒与本地处理延迟 |
| 来源 `real` 或 `simulation` | 将真实课堂与模拟测试严格分开统计 |
| 用户观察的横幅/锁屏/声音/振动结果 | 确认系统通知实际可见性 |

默认不记录账号名、Cookie、Authorization、二维码票据、题干和答案。诊断导出只使用允许字段，不把整份原始网络响应写入日志。

### 两个重要的测量区别

1. “事件已收到”“通知已提交”“用户实际看到/听到提醒”是三个不同结果。ADB 和日志能证明前两项；第三项需要用户观察，或后续通过可用的屏幕镜像检查，并不能仅凭 `notify()` 调用成功断言。
2. 没有老师侧的发布时间或可信时间基准时，只报告“本 App 收到事件到提交系统通知”的本地耗时。微信界面显示时间可以辅助对照，但不冒充精确的老师发布到用户看到的端到端耗时。

## 3. 日常课堂中的测试安排

### 10 月 9 日前：不依赖老师发题的实验

1. 准备 Android 构建工具和可安装通知验证 APK。
2. 检查普通版雨课堂登录、账号身份和入课操作；真实登录由用户完成。
3. 用模拟事件验证权限、横幅、锁屏展示、声音/振动、重复与过期过滤。
4. 加入网络测试链路后，测试前台服务、休眠、网络切换和重连。单纯本地定时通知不能证明后台 WebSocket 可用。
5. 记录默认电池策略与按指引调整后的表现，明确两种条件。

USB 连接通常会给手机充电，会改变自然 Doze 条件。自然锁屏测试需在不充电、静止等实际条件下进行；必要时另做官方支持的受控休眠实验，并在实验后恢复状态。两种结果分别记录，不把插线调试时短时锁屏当作长期后台验证。[Doze 测试说明](https://developer.android.com/training/monitoring-device-state/doze-standby)

### 10 月 9 日：真实课堂对照

- 用户正常进入课堂，再明确启动辅助 App 的课堂监听；若入课接口可能记录签到，点击前说明。
- 以微信雨课堂中实际出现的题目作为可观察对照，按课堂自然发题机会测试切换 App 和锁屏。
- 记录题目出现、辅助 App 是否收到、是否提交通知、实际展示形式与中断情况。
- 锁屏时要验证何时进入休眠，不能只测试刚锁屏的几秒。
- 结束课堂后导出报告；能找到每一次对照记录时才计算可观察的漏提醒数量。

日常课堂的题目数量、题型、发布时间不可控制，因此一堂课中没有失败并不足以验证全部场景。缺少样本的场景保持“未验证”，以后补齐。人工先标记每一次提醒失败的发生时间，即使暂时无法定位原因也保留证据。

## 4. 是否部署服务器会带来什么后果

| 对比项 | 纯手机监听 | 电脑/服务器监听 + 系统推送 |
| --- | --- | --- |
| 数据连接位置 | 手机维持雨课堂连接 | 持续在线监听端维持连接 |
| 锁屏断联 | 受 Doze、前台服务和厂商管理影响 | 雨课堂采集更少受手机休眠影响；手机推送仍有自己的限制 |
| 耗电 | 手机承担心跳、网络和重连 | 手机主要接收推送，预计减少长连接负担，具体收益需测量 |
| 使用条件 | 安装 App、登录、选择课堂；可能要配置后台允许状态 | 额外需要持续在线监听端、网络、可用推送接入与相应设备注册 |
| 会话凭据 | 保存在手机私有空间 | 通常还需保存在监听端；用户需接受其存储位置 |
| 成本 | 没有新增服务器租赁费；仍有测试与分发成本 | 自有电脑要保持开机联网；租赁服务器有持续费用；还需维护更新和故障处理 |
| 新故障点 | 手机进程、网络、系统提醒 | 额外增加监听端、推送服务和设备注册的故障点 |
| 多品牌适配 | 标准 API 加各厂商实测 | 还需要适配可用厂商推送或 FCM，不能只接小米推送就覆盖所有手机 |
| 雨课堂协议变化 | 需要更新 App | 监听端协议可集中更新，手机仍可能需要更新推送或交互部分 |

“服务器”不必是一台付费云主机：自有电脑也能承担监听，但必须在课堂期间持续在线。电脑关机、休眠或网络断开时，这一路线就不能正常采集课堂事件。

服务器不会自动获得教师题目或官方开放权限，仍需要用户的有效雨课堂会话，并面对相同接口变化、过期和入课凭据问题。它也不能消除用户关闭通知、手机断网和系统提醒展示限制。

若未来启用推送，应优先使用可展示通知的系统通道，而不是假定 App 进程随时能被唤醒接收透明消息。小米自己的系统通道与其他系统条件不同；FCM 客户端也有 Google 服务前提，需按真实设备核验。[小米产品说明](https://dev.mi.com/distribute/doc/details?pId=1533)、[小米常见问题](https://dev.mi.com/xiaomihyperos/documentation/detail?pId=1545)、[FCM 客户端要求](https://firebase.google.com/docs/cloud-messaging/android/get-started)

**当前决策：纯手机优先，不部署服务器。** 只有目标设备在说明清楚的可接受配置下仍无法满足后台要求，或多品牌验证表明本地路线有实质覆盖缺口时，再拿实验结果讨论架构变化。

## 5. 建议的首版范围

| 范围 | 建议 |
| --- | --- |
| 数据源 | 普通版雨课堂 |
| 平台 | Android 16，按标准 API 设计多品牌兼容 |
| 首个验收设备 | Xiaomi 14；其他机型在完成对应实测前列为待验证 |
| 运行形式 | 独立辅助 App，纯手机运行 |
| 账号与课堂 | 首版单账号、单课堂；用户选择课堂并明确开始/停止监听 |
| 入课行为 | 手动点击；操作前说明可能记录签到 |
| 提醒 | 新题系统横幅、锁屏通知，配合声音/振动；不依赖题干完整下载 |
| 核心可靠性功能 | 登录失效提示、连接状态、重连、发布去重、历史回放与延时区分 |
| 可观测性 | 脱敏诊断报告、测试通知、实际提醒反馈 |
| 分发 | 先作为验证 APK，不以一台机型结果宣称全品牌已验证 |

多品牌是实现目标，不缩减成“小米专用”。首版兼容设计与“已经测试通过的机型”分别表述；扩大已验证范围需要更多 Android 16 真机和日常课堂样本。

## 6. 80% 把握与工程启动

80% 是用户提出的工程启动判断门槛，本轮没有统计数据可以计算一个真实成功概率。目前不足以对“普通版真实发题 + 所有 Android 16 品牌锁屏稳定”给出这样的判断。

可以先完成工程准备和最小验证骨架。它们用来取得判断所需的证据，不作为完整提醒功能已成功的结论。正式课堂监听工程以以下关口为依据：

1. 普通版账号独立授权成功，能取得合法课堂身份和监听凭据；手动入课行为与用户要求一致。
2. 与微信同课堂并行使用时能接收真实新题，且不会破坏正常微信课堂会话。
3. Xiaomi 14 上切换 App、自然锁屏与受控休眠实验的数据链路和通知行为明确，并能区分失败原因。
4. 多品牌实现不依赖小米专有保活接口，其他 Android 16 机型的验证路径可执行。

其中真实发题证据最早安排在 10 月 9 日课堂中取得；若此前没有真实课堂，不会用模拟成功替代它。满足这些关口后，再评估收敛首版的实施把握并推进完整功能；不再重复询问已经明确授权的工程动作。
